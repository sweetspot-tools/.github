# Contributing to Sweetspot Tools

Thank you for your interest. This guide applies to every public repository of the
[sweetspot-tools](https://github.com/sweetspot-tools) organization:

| Repository | What it is | License |
|---|---|---|
| [fairy-tapes](https://github.com/sweetspot-tools/fairy-tapes) | Fairy Tapes, a suite of VST3 audio plug-ins (C++, VST3 SDK, VSTGUI) | GPL-3.0 |
| [swingers](https://github.com/sweetspot-tools/swingers) | MIDI drum map converter, plug-in and standalone (C++, JUCE) | AGPL-3.0 |
| [turn-me-on](https://github.com/sweetspot-tools/turn-me-on) | Browser MIDI controller for outboard gear (Vue, TypeScript) | MIT |
| [brand](https://github.com/sweetspot-tools/brand) | Logos and their generator scripts | CC BY-ND 4.0 |

Please also read our [Code of Conduct](CODE_OF_CONDUCT.md). To report a security issue, do not open a public issue:
read the [security policy](SECURITY.md).

## Before you start

- **Bugs:** search the existing issues first, then open one with the bug report template. Include the host (DAW,
  browser or operating system), the versions, the steps to reproduce, and what you expected.
- **Features and larger changes:** open an issue to discuss the idea before writing code. Each plug-in follows a written
  design and a shared visual language, so agreeing on the design first saves you from writing a pull request that
  cannot be merged.
- **Small fixes** (typos, docs, obvious one-line bugs) can go straight to a pull request.
- **Brand assets** are not open to derivative works: propose changes in an issue of the brand repository.

## Licenses of contributions

You contribute under the license of the repository you contribute to. Make sure you are allowed to: code copied from
other projects must have a compatible license, and its origin and license must be stated in the pull request.

## AI-assisted contributions

You are welcome to use AI tools. You stay responsible for what you submit:

- Review, test and understand every change before you open the pull request. Write the description yourself, in your
  own words.
- Make sure you are allowed to submit it: the tool's terms must let you license its output, and it must not reproduce
  third-party code you cannot license.
- Large or complex changes written mostly by a tool, without careful human review, will not be accepted. Mass-opened
  issues or pull requests generated by a tool are closed without review.

## Development workflow

1. Fork the repository and create a branch from the default branch (`master` or `main`).
2. Make focused changes: one topic per pull request.
3. Add or update tests for every behaviour change.
4. Update the documentation affected by your change.
5. Run the checks for the repository you are working in (see its README).
6. Open a pull request and fill in the template.

### Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(pillow-talk): add tempo sync to the ducking release
fix(the-stripper): keep the drive model after reloading a project
docs(swingers): document the drum map file format
```

Common types: `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `chore`. Use the plug-in or area as the scope when it
helps. Write the subject in English, in the imperative mood.

### Language

Code, comments and commit messages are written in English.

## Pull request review

- A maintainer will review your pull request as soon as possible. This is a small project, so please be patient.
- CI must pass before a pull request can be merged.
- We may ask for changes, or close pull requests that do not fit the project's direction. When we do, we will explain
  why.

## Organization profile images

The panel images in `profile/images` are rendered from the HTML previews of the Fairy Tapes repository with
`tools/render-previews.js` (instructions at the top of the script). Re-run it when a preview changes.
